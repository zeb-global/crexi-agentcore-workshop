CREXi AgentCore Workshop

Learn AgentCore Harness by building two real agents

Five build steps, about 2 hours 20 minutes hands-on. Each one names the exact file and field you fill in, what it teaches you about how Harness actually works, and the verified reference answer, so you can check your own work without guessing whether it is right.

~2h 20m hands-on 5 build steps 2 agents built on the participant-exercise branch

Dana Reyes, an investor, is watching multi-family listings in Columbus, Ohio: 50 to 150 units, up to $12,000,000, cap rate at or above 6.50 percent. Marcus Hale, a broker, owns one of them, and the only record of its real condition sits in a legacy deal desk with no API. Assembling one honest answer from four disconnected sources is the exercise.

How to use this guide

You only ever touch six files: app/investorAgent/harness.json, app/investorAgent/system-prompt.md, app/brokerAgent/harness.json, app/brokerAgent/system-prompt.md, backend/confirmation.py, and backend/pricing.yaml. Everything else — agentcore/, infra/, services/, frontend/ — is pre-built. If a step seems to need touching anything else, re-read it; ask a facilitator before you do.

Each step gives you the field, what it means, and what it's teaching you about how Harness works. Try that first. The green reveal the answer panel underneath is the verified reference content — open it to check your work or to unstick yourself, not as the first move.

Setup

Get your environment running

Deploy a working stub end to end before touching any agent config.

15 min no files — setup only

What you're doing

A Harness is just a config file plus a system prompt — there's no agent loop to write. Both harnesses in this repo already deploy, right now, as dumb stubs (a name, a model, no tools, no memory). The goal here is only to prove your own environment and AWS account work: deploy the stub, open the chat UI, get a plain reply with no personalization and no tools. The next five steps build this same stub up into a real agent, one piece of Harness config at a time.

terminal
# pick a WORKSHOP_ID unique to you: letters and digits only, must start with a letter
export WORKSHOP_ID=jsmith01
export WORKSHOP_SECRET=some-secret-only-you-know
export AWS_REGION=us-west-2

make preflight
make bootstrap WORKSHOP_ID=$WORKSHOP_ID WORKSHOP_SECRET=$WORKSHOP_SECRET
make wire-backend-env WORKSHOP_ID=$WORKSHOP_ID
make dev
First run takes longer. make bootstrap provisions infra/.venv, backend/.venv, and two node_modules directories before it deploys anything — add a few minutes the very first time. Every step here is safe to re-run if a credential expires mid-deploy.

  "strategies": ["SEMANTIC", "SUMMARIZATION", "USER_PREFERENCE"],

Step 3 · Set allowedTools

Set allowedTools to ["@market-data/*"] for now (the next step adds one more entry). Note the @ prefix and the trailing /* glob — both matter.

Why the @ prefixA bare tool name in allowedTools only matches AWS's fixed built-in tool identifiers. market-data is a custom-named Gateway tool from the harness author's own perspective, so it must be referenced as @market-data/* — the same way the next step's code-interpreter tool needs @code-interpreter, not a bare name. Getting this wrong doesn't error at deploy time; it silently rejects every call with "Unknown tool" at runtime, which is a much harder bug to trace back to one missing character.

Step 4 · Write the real system prompt

Replace the placeholder in system-prompt.md with the real investor-assistant prompt. At minimum it needs to teach the model: never state a figure that didn't come from a tool call or stored memory this turn; where each field actually lives (units and price from search_listings / get_listing, market comps from get_market_comps); to apply a returning user's stored criteria without asking them to repeat it; and to be proactive — call the tools immediately once intent is clear, rather than asking permission to search.

app/investorAgent/system-prompt.md
You are CREXi's investor-facing assistant for commercial real estate. You help
investors find and evaluate multi-family listings.

Grounding rules:
- Never state a property name, address, unit count, price, or any figure
  that did not come from a tool call this turn or from memory context
  clearly labeled as this user's prior stored criteria. If you are not sure
  a property exists, call search_listings or get_listing to check.
- Units and asking price come from search_listings / get_listing. Market
  cap rates and comparable sales come from get_market_comps.
- When a returning user has stored criteria (market, unit range, asking
  price ceiling, minimum cap rate, value-add preference), apply them without
  asking the user to repeat them.
- Be proactive: once the user's intent is clear (e.g. "what's new in
  Columbus"), immediately call search_listings with their stored or stated
  criteria -- do not stop to ask permission to search. Never invent a
  result instead of calling a tool.
- Never state internal system data: listing IDs, database version numbers,
  raw tool-call statuses, timestamps, session IDs. Refer to a property
  only by its name.
- Never narrate your own tool-calling mechanics or retries to the user.

Style:
- Be concise and specific to the user's stated or stored market and
  criteria. Plain, professional text. No emojis or decorative symbols.

Step 2 · Teach it where NOI lives, and that it must not do the math itself

This is the crux of this step. Net operating income exists only inside each listing's T-12 operating statement PDF — it is not a field on the listing, and the model must never estimate it. It has to call get_document_text(listingId, "T12_2025.pdf"). And once it has (name, listingId, units, askingPrice, noi) for every candidate, it must not calculate cap rate, DSCR, or cash-on-cash itself — it has to run that arithmetic as an actual Code Interpreter tool call that executes Python and returns real stdout.

Why this is enforced this hardA language model typing plausible-looking numbers is indistinguishable from a language model doing arithmetic correctly — until the two disagree. Routing the calculation through Code Interpreter means every number in the comparison table traces to code that actually ran, not to a guess dressed up as a calculation.

The underwriting formula, exactly:

MetricFormula
Cap ratenoi / askingPrice * 100, 2 decimals
Price per unitaskingPrice / units, rounded
DSCR / cash-on-cashassuming LTV 0.65, rate 6.5%, 30-year amortization
Meets criteriacap_rate >= investor's minimum (default 6.5 if none stored)

The executed code's last printed line must be exactly one line of compact JSON — no markdown, no code fence — which the UI reads directly out of Code Interpreter's own stdout to render the comparison card. There is no separate submission call.

the last line Code Interpreter must print
{"type":"underwriting_comparison","criteria":{"cap_rate_min":<n>},
 "properties":[{"name":..,"listingId":..,"units":..,"askingPrice":..,
 "noi":..,"cap_rate":..,"price_per_unit":..,"dscr":..,"cash_on_cash":..,
 "meets_criteria":true|false}],"recommended":{"name":..,"listingId":..}}

Step 3 · Watch two isolation violations fail

Neither of these needs a new file — drive them from the CLI against harnesses you've already deployed:

  1. Cross-role tool call, denied by IAM. Use agentcore invoke --allowed-tools to force investor's already-deployed harness to attempt a listing-ops call it was never attached to. Investor's own execution role was never granted invoke permission on that gateway's Lambda — the override lets the model try, and AWS denies it. This is a real IAM boundary, not a missing-tool error.
  2. Cross-actor memory read, returns nothing. Ask brokerAgent (signed in as marcus) to recall Dana's stored criteria. It gets nothing back, because managed memory is scoped by actorId — marcus's namespace and dana's simply don't intersect.
How you know it workedBoth denials should be visible, not silent: the IAM one as an explicit AccessDenied in the tool-activity trace, the memory one as an empty or generic response rather than an error. If either one succeeds, isolation is broken — stop and check which harness's config leaked into the other's.

Step 2 · Teach the prompt the legacy-desk flow and the price-change flow

Two behaviors to add to system-prompt.md:

  • Legacy desk: call get_legacy_credentials first, by itself in that turn (never alongside another tool call), never print the returned username or password in a reply, then use the browser tool to log in and navigate to the listing's rent roll.
  • Price change: always call get_listing fresh immediately before proposing a change — never trust get_change_log or an earlier value in the conversation, since history is not current state. Then call confirm_listing_change (again, by itself) with the old and new price. Its result carries an approvalToken that must be passed, unmodified, to update_listing_price.
Why "by itself, never in parallel"Confirmed by direct testing against the real event stream: a model requesting an inline function in parallel with another tool call in the same turn makes the harness hand back every pending tool-use block unresolved, not just the inline one. The system prompt is the only lever to prevent this — there's no harness-side setting for it.

- This information exists ONLY in a separate legacy system with no API,
  reachable only through the browser tool, as the signed-in broker.

  turn -- never alongside another tool call in the same turn.

- Use the browser tool to navigate to the login page, submit the

  ?listing=<listingId> to read the rent roll and deferred maintenance.

Changing a listing's asking price:
- Always call get_listing to get the CURRENT price fresh, right before
  proposing a change -- even if you recall a price from earlier in this
  conversation or from get_change_log. get_change_log is history, not

- Once you know the current price and the broker has told you the new

Step 3 · Implement the round trip in confirmation.py

Two functions, both starting as NotImplementedError:

resolve_legacy_credentials(actor) — look up actor (the real, verified username from the JWT, never anything the model supplied) in the crexi-{WORKSHOP_ID}-legacy-creds DynamoDB table and return the username/password. Return an {"error": ...} dict, not a crash, if there's no account on file.

mint_price_change_approval(...) — called only after the human has said yes. Read the listing fresh from DynamoDB (never trust a version the caller passed in), mint a fresh uuid4 token, and store it in the approvals table with the listing ID, old and new price, the listing's current version, the actor, session ID, mint time, and an expiry.

The actual trust boundaryBoth functions receive actor from main.py, which came from a verified Cognito JWT — never from anything the model said. That's what makes the approval token meaningful: the MCP write handler only has to check that a valid, unexpired, unused token exists for this exact change. It never has to know or trust who's calling it.
Reveal the answer — both functions
backend/confirmation.py
def resolve_legacy_credentials(actor: str) -> dict:
    creds_table = _dynamodb.Table(f"crexi-{config.WORKSHOP_ID}-legacy-creds")
    item = creds_table.get_item(Key={"username": actor}).get("Item")
    if not item:
        return {"error": f"No legacy-desk account on file for {actor!r}."}
    return {"username": item["username"], "password": item["password"]}


def mint_price_change_approval(actor: str, listing_id: str, old_price: int, new_price: int, session_id: str) -> dict:
    listings = _dynamodb.Table(config.LISTINGS_TABLE)
    approvals = _dynamodb.Table(config.APPROVALS_TABLE)

    listing = listings.get_item(Key={"listingId": listing_id}).get("Item")
    if not listing:
        return {"approved": False, "reason": f"No listing {listing_id!r} found."}

    token = str(uuid.uuid4())
    approvals.put_item(Item={
        "approvalToken": token,
        "listingId": listing_id,
        "newPrice": int(new_price),
        "oldPrice": int(old_price),
        "version": int(listing["version"]),
        "actor": actor,
        "sessionId": session_id,
        "mintedAt": time.strftime("%Y-%m-%dT%H:%M:%SZ", time.gmtime()),
        "expiresAt": int(time.time()) + config.APPROVAL_TOKEN_TTL_SECONDS,
    })
    return {"approved": True, "approvalToken": token}

Where config ends and code begins

5 minutes, facilitator-led. Nothing here is graded or files touched.

Run agentcore export harness --name investorAgent and look at what comes out: a real, substantial Strands agent under app/investorAgent/ — a BedrockAgentCoreApp, MCP client setup, a Code Interpreter wrapper, and the full system prompt carried over verbatim. This is the agent loop you never had to write, now as code you own.

Then the fork this creates: the managed Harness loop cannot be interrupted mid-run. For a confirmation step like the broker's price-change flow, that's fine — the pause is a designed part of the loop. For a persistent, site-wide assistant that needs to be stoppable at any point in an arbitrary long-running task, that's the exact moment a team reaches for the exported Strands code instead of the managed Harness.

Read the export notes. Every export produces an EXPORT_NOTES.md alongside the generated agent, listing anything the exporter couldn't automate — missing files, IAM policies, manual steps. A clean export says "no manual steps required"; anything else needs handling before the exported agent will run.
